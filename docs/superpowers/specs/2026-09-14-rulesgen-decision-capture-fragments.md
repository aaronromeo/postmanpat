# rulesgen: Cluster Decision capture and fragment rendering

Delivery stage 03 of the rulesgen effort (stub: `docs/issues/03-rulesgen-decision-capture-fragments.md`; architecture: `docs/adr/0002-suppression-via-report-annotation.md`, `docs/adr/0003-rulesgen-coexists-with-python-generator.md`, `docs/adr/0004-scheduled-analyze-file-ingestion.md`, `docs/adr/0005-fragments-manual-merge-preserved.md`; vocabulary: `CONTEXT.md` — Cluster Decision, Review Queue, Pending Merge, One-Time Cleanup, Ongoing Cleanup, Suppressed). Parity reference: `bin/postmanpat-generate-rules.py`.

## Problem Statement

The Review Queue is still read-only: seeing a Pending Cluster tells me it needs a decision, but making one still means SSH, the Python generator script, and its interactive, one-session checkpoint. Every rule, decline, and ignore is decided in a terminal prompt and recorded in the script's Generation Checkpoint — a record of what was *asked* that deliberately diverges from what candidates rulesgen is the system of record for (ADR 0003). I want to make the decision — Generate / Decline / Ignore / Snooze — for each Pending Cluster, on each rule-type lane, from the queue page itself; have each decision persist; and have the Generated rules and Ignored entries appear as hand-mergeable fragment files in the mounted config directory, matching exactly what the Python script would have produced.

## Solution

Each Pending Cluster on the Review Queue page gains a per-lane decision block (pending cluster → per-lane forms per the data-driven lane map: watch, One-Time Cleanup, Ongoing Cleanup; `recipient_tag_lens` offers watch only). Each block offers **Generate** (a script-parity rule form), **Decline**, **Ignore**, and **Snooze**. Generating produces a rule form pre-filled with script-parity defaults derived from the Cluster's Lens Key, signals, and examples — watch lanes emit client matchers, cleanup lanes emit server matchers including the one-rule-per-recipient-alias split and the sanctioned `age_window.min` extension (empty default for One-Time Cleanup, `30d` for Ongoing Cleanup, never offered on watch). Ignoring on the watch lane asks "also ignore for cleanup?" exactly like the script's `i` cross-offer. Every decision persists in the existing `decisions` table (INSERT-only, no migration). Generated rules and Ignored entries render wholesale into four fragment files (watch, cleanup-ongoing, cleanup-onetime, ignore) in the mounted fragment dir; fragments always equal the full decided set (ADR 0005 — merge marking is stage 04, so every decision renders in this stage). Snoozed lanes are hidden until a newer ingested report re-contains the Cluster, which clears the snooze. A Decisions view lists clusters whose lanes are all decided and offers per-decision reversal; reverting undeclines a lane and the Cluster re-enters the queue.

## User Stories

1. As the operator, I want each Pending Cluster to show decision controls per rule-type lane, so I can decide a Cluster without leaving the queue page.
2. As the operator, I want the per-lane controls to match the data-driven lane map, so `recipient_tag_lens` offers watch only while list/sender Clusters offer all three lanes.
3. As the operator, I want a Generate control per lane that opens a script-parity rule form, so a generated rule's fields and defaults match the Python script exactly (ADR 0003).
4. As the operator, I want a Decline control per lane, so a Cluster I have deliberately dismissed leaves the queue for that lane.
5. As the operator, I want an Ignore control per lane, so I can author an Ignore List entry for the Cluster's identity without the terminal prompt.
6. As the operator, I want a Snooze control per lane, so a Cluster I want to defer stays quiet but not permanently decided.
7. As the operator, I want every decision recorded per (Cluster, lane) and persisted so it survives service restarts and container redeploys.
8. As the operator, I want a fully decided Cluster (no undecided lane left) to leave the queue, so only genuinely undecided Clusters are listed.
9. As the operator, I want the watch Generate form for `list_lens` to pre-fill `list_id_regex` with the escaped `ListID` key, so I rarely need to type the matcher.
10. As the operator, I want the watch Generate form for `sender_unsub_lens` to pre-fill `sender_regex` with the escaped, de-duplicated sender domains (cluster `SenderDomains` plus domains derived from `FromList`), so sender watch rules start from the right identity set.
11. As the operator, I want the watch sender form to offer the optional `list_unsubscribe` boolean (defaulted from `HasListUnsubscribe`), `replyto_regex`, and `recipients_regex` with escaped example-domain defaults, so every script option is reachable from the form.
12. As the operator, I want the watch Generate form for `recipient_tag_lens` to pre-fill `recipient_tag_regex` with the escaped recipient-tag key, so tag-based watch rules are one-click.
13. As the operator, I want every watch rule to carry an `actions` choice (delete by default, or move with a destination), so rules are fully formed at capture time.
14. As the operator, I want the cleanup Generate forms (one-time and ongoing) to pre-fill `list_id_substring` / `sender_substring` from the Cluster keys, so cleanup rules start from the Cluster identity.
15. As the operator, I want cleanup rules to remember a default source folder of `INBOX`, so the common case needs no typing.
16. As the operator, I want the cleanup sender form to offer the same optional extras the script does (`list_unsubscribe`, `replyto_substring`, `recipients`) with example defaults, so no script capability is lost in the web path.
17. As the operator, I want cleanup rules emitting more than one `recipients` value to split one-rule-per-alias with the `{name} ({recipient})` naming, because server matchers AND multiple recipients into a single rule that can never match.
18. As the operator, I want `age_window.min` offered on both cleanup lanes — empty default on One-Time Cleanup, `30d` on Ongoing Cleanup — and never on watch, so the sanctioned extension behaves as designed (ADR 0003).
19. As the operator, I want an Ignore on the watch lane to offer "also ignore for cleanup?", matching the script's `i` cross-offer, so one answer can cover both Ignore Lists.
20. As the operator, I want an Ignore decision to record the Cluster's identity per ADR 0002 — `list_ids` for `list_lens`, `sender_domains` for `sender_unsub_lens`, `recipient_tags` for `recipient_tag_lens` — so `sender_addresses` and `subject_substrings` stay hand-authored.
21. As the operator, I want a watch-suppressed Cluster to offer no watch controls and a cleanup-suppressed Cluster no cleanup controls (half-suppressed shown with its badge), so Suppressed annotations disable the corresponding lane.
22. As the operator, I want a Cluster suppressed for both lanes to never enter the queue at all, so Fully Decided noise stays out.
23. As the operator, I want every generated rule persisted with its full payload, so fragments can be rendered and re-rendered from the store alone.
24. As the operator, I want generated watch rules to render into a `watch` fragment file shaped like the script's `--watch-out` YAML, so the fragment mirrors the offline output exactly.
25. As the operator, I want generated One-Time Cleanup rules to render into a `cleanup-onetime` fragment and Ongoing Cleanup rules into a `cleanup-ongoing` fragment, each shaped like the script's `--cleanup-out` YAML per lane, so the two cleanup careers stay distinct.
26. As the operator, I want an Ignore fragment file rendering the aggregated, de-duplicated Ignore entries under the analyze config's `ignore:` shape (watch and/or cleanup sides), so I can hand-merge it into the analyze config (ADR 0002).
27. As the operator, I want the watch and both cleanup fragment files always written (empty `rules: []` when a kind has nothing) and the ignore fragment written only when it has entries, all re-rendered wholesale whenever any decision changes — so a fragment always equals the full decided set, never accumulates stale or duplicate rules (ADR 0005), and an empty ignore fragment can never be merged over the hand-maintained analyze config's `ignore:` section.
28. As the operator, I want fragment rendering to be deterministic and idempotent, so re-rendering identical state produces byte-identical files.
29. As the operator, I want rulesgen to never touch the live watch/cleanup/analyze configs, so the generate → review → merge workflow and hand-maintained ordering are preserved (ADR 0005).
30. As the operator, I want a Snoozed lane's Cluster to disappear from the queue and stay hidden across reports, so deferral genuinely quietens it.
31. As the operator, I want a Snoozed Cluster to reappear in the queue once a newer ingested report re-contains it, because the window only means "mail arrived for it again" (ADR 0004).
32. As the operator, I want a Decisions view listing clusters whose lanes are all decided (not pending), so I have a record of what I have already worked through.
33. As the operator, I want a revert control per decision in the Decisions view, so a mistaken Generate/Decline/Ignore/Snooze can be undone.
34. As the operator, I want reverting a decision to make that lane undecided and the Cluster to re-enter the queue, so a reversed Cluster is immediately pending again.
35. As the operator, I want fragment files to re-render after a revert, so the fragments stay consistent with the store.
36. As the operator, I want the queue page's decision forms to carry script-parity escaped defaults (Go `regexp.QuoteMeta`, matching Python `re.escape`), so watch regex defaults are exactly what the script would offer.
37. As the operator, I want generated YAML to emit real, unquoted YAML booleans, so fragment files merged into the live configs parse in `appconfig.Load` (the quoted-bool bug the Python emitter exists to avoid).
38. As the operator, I want `serve` to take the fragment directory as a flag, so deployment mounts one writable dir and the service stays pointed at the right place.

## Implementation Decisions

- **Decision capture reuses the empty `decisions` table unchanged** (INSERT-only, no migration): primary key (`cluster_id`, `lane`), columns `decision` in {`generated`, `declined`, `ignored`, `snoozed`}, `decided_at`, and a nullable JSON `payload`. `generated` payloads are the rule object (ordered so YAML shape survives); `ignored` payloads are the identity map (ADR 0002 field per lens); `declined` and `snoozed` carry null payloads. `PendingClusters` and `hasUndecidedLane` need no change — any decision row for a lane already marks it decided.
- **Store methods.** `Decide(clusterID, lane, decision, payload)` upserts a decision with `decided_at`; `Revert(clusterID, lane)` deletes the row; `ListDecisions()` returns decisions for clusters whose lanes are all decided (the complement of the pending set), with cluster context for the view. A new ingest-time step `ClearSnoozed(clusterIDs)` deletes `snoozed` decisions for every Cluster re-contained in a newer report, invoked from the ingestion path — this is the whole Snooze semantics (ADR 0004: "hidden until a newer report containing the Cluster arrives"). A Cluster that stays absent keeps its snooze.
- **Builders are pure functions in `rulesgen`** (the parity-critical core), shaped `(cluster, lane, formInputs) → rule`. Defaults are computed from Cluster keys/signals/examples at form-render time: watch regex defaults use Go `regexp.QuoteMeta` (parity with `re.escape`); the `sender_regex` default merges cluster `SenderDomains` with domains derived from `FromList` values, de-duplicated preserving order (parity with the script's `dict.fromkeys` merge). Cleanup substring defaults pass cluster keys through raw, exactly as the script does. `list_unsubscribe` defaults from `HasListUnsubscribe` when it is a boolean. Action defaults to `delete`; `move` requires a destination.
- **One-rule-per-alias split lives in the cleanup sender builder.** More than one `recipients` value yields one rule per alias, each named `{name} ({recipient})` with a single-element `recipients` — parity with `build_cleanup_rule_sender` (server matchers AND multiple `recipients`, so one multi-alias rule can never match).
- **`age_window.min` is the only sanctioned extension over the script** (ADR 0003): offered on both cleanup lanes with defaults `""` (One-Time Cleanup — all ages, emitted as no `age_window`) and `"30d"` (Ongoing Cleanup). Never offered on watch. The emitted rule carries `server.age_window.min` only when non-empty.
- **Fragment rendering is a pure function over store decisions** (ADR 0005 wholesale re-render). `watch.yaml` (`rules:` list of generated watch payloads), `cleanup-ongoing.yaml`, and `cleanup-onetime.yaml` (server-shaped `rules:` lists per lane) are always written — an empty `rules: []` when a kind has no decision — while `ignore.yaml` is written only when that kind has at least one entry. This mirrors the script exactly (`build_ignore_fragment` returns `{}` when both sides are empty, and the script omits the ignore output in that case): empty rule fragments are cheap and harmless, and an empty `ignore:` block is never dropped in front of the hand-maintained analyze config's `ignore:` section. Ignore identity values aggregate under that `ignore:` shape, sides omitted when empty, values sorted and de-duplicated per field (parity with `build_ignore_fragment`/`dedup_ignore_entries`). Ordering of rules is deterministic (stable per run) so re-rendering identical state yields byte-identical files. Merge-marking does not exist yet (stage 04): every decision renders. Live configs are never written.
- **YAML emission via `gopkg.in/yaml.v3`** (already a dependency) from ordered structs, not hand-built strings: struct field order reproduces the script emitter's key order (name, client/server, actions), and native Go bools emit as real unquoted `true`/`false` — the exact property the Python emitter exists to guarantee because the Go config parser rejects quoted bools (see `fix/yaml-generator-bool-quoting`; Go-side must not regress it). Fragment content equals the script's output shape for equivalent inputs.
- **HTTP surface extends the existing server.** `NewServer` grows a fragment renderer dependency (fragment dir) so decision-changing requests re-render immediately. Routes: the queue page renders per-lane decision forms (only for undecided, non-suppressed lanes; suppressed lanes show their badge without controls); `POST /decide` (fields: `cluster_id`, `lane`, `decision`, plus rule-form fields when generating) captures via the store and re-renders fragments; `POST /revert` (`cluster_id`, `lane`) deletes the decision and re-renders; `GET /decisions` renders the Decisions view. POSTs redirect (303) back to the queue or the Decisions view. No auth — the private-network trust boundary is unchanged from stage 02. All values are server-side re-validated (unknown lane/decision rejected; required fields enforced) and the queue page continues to HTML-escape Cluster data.
- **`serve` gains a required `--fragments` flag** (writable mounted fragment dir). `ServeOptions` passes it through to the server. Ingest now also performs `ClearSnoozed` for re-contained Clusters, trimming before pending computation.
- **Folders field, simplification:** the script's running `default_folders` (last-used across clusters in one session) is not replicated; the operator expects the source folder to only ever be `INBOX`. The cleanup forms therefore present one folders field defaulting to `INBOX` (kept editable for future flexibility, no session memory).

## Testing Decisions

Good tests verify external behavior only — what a decision persisted and its fragment rendered, what the queue and Decisions pages show, what idempotent re-render means as observable bytes — never internal function wiring. The corpus pins parity contractually (ADR 0003), because the Python suite is not in CI. Stage-02 precedents carry over: real temp SQLite databases, real fixture report files on disk, `httptest` against the real handler.

- **Generation seam (new; the parity-critical core).** A committed golden corpus under `testdata/parity/`: one JSON input (Cluster with keys/signals/examples/suppressed + a fixed decision payload) per interesting (lens × lane × shape) case — watch list/sender/recipient-tag, cleanup list/sender one-time and ongoing, the multi-alias recipient split, `age_window.min` on/absent, ignored identity per lens, escaped-default expectations. Each case's expected YAML is derived from the Python script's current behavior (driven with canned answers; a one-off authoring step, not a CI step). The Go suite walks the corpus and asserts its builder/fragment output bytes-equal the golden YAML; the Python suite asserts the same corpus. A regression in either implementation fails its own suite, and CPR nearly everywhere across the builders is free because they are pure functions.
- **Store seam (extended).** Decision lifecycle against a real temp DB: `Decide` persists and `PendingClusters` excludes the decided lane; a fully decided Cluster leaves the pending set; `Revert` makes the lane undecided and the Cluster pending again; `ClearSnoozed` on re-ingest makes a Snoozed Cluster reappear while an absent Cluster keeps its snooze; run-parity of the four outcomes; decisions survive reopen (close + reopen the same DB file).
- **HTTP seam (extended).** `httptest` against the real handler over a real store and temp fragment dir: submitting `POST /decide` persists a decision and writes the fragment file; the fragment bytes equal expected YAML; suppressed lanes render no controls; `POST /revert` returns the Cluster to the queue and re-renders; `GET /decisions` lists non-pending decisions; unknown lanes/decisions are rejected; the page remains HTML-escaped; fragment re-render is idempotent byte-wise.
- **Ingestion seam (extended).** Re-ingesting a newer report that re-contains a Snoozed Cluster clears the snooze; re-ingesting an unchanged report leaves decisions untouched; idempotency holds with decisions present.
- **CLI wiring.** Flag defaults and required-flag behavior for `--fragments`, in the existing thin cli test style.
- **Python parity suite stays out of CI but is run when touching shared expectations** (`cd bin && python3 -m unittest discover -p "test_*.py"`); the corpus replaces the manual "diff the YAML" recommendation from the handoff.

## Out of Scope

- Merge marking and the Pending Merge view — stages 04/05 (ADR 0005); every decision renders in this stage.
- The Pending Merge runbook and the `mark-merged` CLI surface — stage 04.
- Authentication, TLS, CSRF, or any exposure beyond the private network.
- Live-mailbox testing from the UI — confirmed direction: rule values are derived from Cluster data read from reports (ADR 0004); rulesgen never opens IMAP.
- Live YAML preview-as-you-type in the generation forms — not confirmed, deferred; the fragment files are the review surface.
- Report retention/history, OTel instrumentation of rulesgen, or syncing decision state with the Python Generation Checkpoint (ADR 0003) — unchanged from stage 02.
- Retiring or editing the Python script beyond the parity corpus; the two record types still deliberately diverge.
